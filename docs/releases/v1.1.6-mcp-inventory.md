# v1.1.6 MCP inventory and merge

Status: v1.1.6. The built-in T3 MCP keeps its existing `t3_*` names and also carries the
`t3code-mcp-v2` names that had no equivalent. The standalone `t3code-mcp-v2` services keep running;
nothing here retires them.

## One network endpoint

The built-in MCP on server-1 is the hub. Its thread, project, environment and instruction tools
already take `environmentId`; a linked environment is called over the existing peer link with that
link's credential and access. There is no second SSH or token layer. An unavailable peer surfaces
as an explicit failure (`unavailable`, `PeerLinkError`, or `capability_denied` when linked
environments are off), never as an empty result.

Instruction tools forward the same way. A machine that has not been upgraded yet answers with a
tool-not-found failure, so mixed-version fleets fail explicitly.

## Paging and caps

Read tools page with `cursor`/`nextCursor`. `limit` tops out at 100 per call on purpose (a
transport guard, not a result cap); callers follow `nextCursor` for the whole set. Message reads
take `maxCharsPerItem`, and `get_message`-style reads return `truncated` so a caller can request the
rest instead of assuming the text ended.

## Not in v1.1.6

`fleet_update_status` and `fleet_update` belong to the v1.1.7 operational track (Settings > About
environment selector, shared updater, dry run). They are not part of this merge.
